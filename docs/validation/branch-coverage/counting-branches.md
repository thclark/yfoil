# Counting branches

Before a minimal set can be chosen, the branches it has to take must be fixed: this page defines them, and every count in the study is out of this total.

The translated set is the subroutines listed in `xtask/fixtures-config/coverage.toml`, measured by gcov on the pristine double-precision reference ([Coverage](../../development/testing/coverage.md)). The *analysis path* is the translated set without the panelling generators and their helpers (`naca.f`, `xgeom.f`, `spline.f`, and `NACA`/`PANGEN` in `xfoil.f`), which the `pangen_*` cases test bitwise ([geometry](../../development/testing/geometry/README.md)). A branch is one outgoing edge of a conditional as gfortran emitted it; the counts below are edges.

## What the statuses mean

A *branch* is one outgoing edge of a conditional as gfortran emitted it for the reference build: an `IF` gives two edges, every operand of a `.AND.`/`.OR.` chain its own pair, a `DO` line the pair of the loop-control test gfortran placed there (iterate again, or leave the loop by its count), and a loop whose back-edge test lands on its last statement a pair there. Which arm is *fallthrough* and which is *jump* is the compiler's choice, so an edge is named by line and index, never by true/false; the source line and the counts of its sibling edges identify the arm. Every count is gcov's on the **reference**: XFOIL 6.99, pristine, double precision, compiled with `-fprofile-arcs -ftest-coverage`. yFoil is not instrumented and its own control flow is never measured; yFoil's side of the claim is the whole-run comparison below, which asserts that on each run of the finite set yFoil reproduces XFOIL's branch trace (iteration counts, IST/ITRAN, LVCONV, SPECCL's ITAL) and values. A branch taken by the finite set is therefore one the reference took on a run that yFoil matched.

Every branch of the analysis path has exactly one of five statuses, drawn in these colours in the branch map:

- **taken by the finite set** (green) — the reference took the edge on at least one run of the `branch-coverage` group, and yFoil matches every run of that group. The set is chosen to take every branch that any finite candidate takes, and the study stops with an error if it does not.
- **taken by the non-finite set** (blue) — the edge is taken only on runs of the `non-finite` group, whose reference output contains `NaN`. In every case found so far XFOIL produced the non-finite value in TRCHEK2, whose transition-point Newton lands on the interval end; the MRCHUE/MRCHDU iterate fallback then puts finite values on the station and the run carries on. These runs cannot be compared whole, because the reference's own 1-ULP twins wander by O(10²) on them. Each edge is tested instead as an **event**: the instrumented reference writes `events.dat` (site, SETBL call, side, station, deciding value) and keeps the state dumps of those calls, and a test in `tests/execution/events.rs` seeds yFoil with XFOIL's exact state entering the call, runs the one subroutine or the one iteration, asserts that yFoil's branch trace records the same event, and compares the result with the reference's dump — NaN where the reference has NaN. (TRCHEK2's `AX ≤ 0` exit, taken many times within one call, is recorded call by call instead — `trchek2_ax_exit.dat`, the inputs of each TRCHEK2 call that takes it — and `tests/subroutine/transition.rs` replays each one.) The non-finite set is part of the test suite (`group = "non-finite"`, tracked), so these branches are covered by tests one call at a time; what is not claimed is that yFoil follows a whole non-finite run. The table *Branches taken only by the non-finite set* names the test of each edge.
- **taken only in pathological cases** (orange) — the edge is taken only by a case of the `pathological` group: copies of the runs that hang in XFOIL's plot label or take hours (known issues §4), which cannot be tests. Those cases are measured only on request (`cargo xtask coverage --per-case --with-group pathological`); the status table says whether this run measured them.
- **not reachable** (grey) — no execution of XFOIL's analysis path takes the edge. Either a recorded code-reading argument says so (*annotated unreachable*, in one of the five classes below), or the edge is the never-taken arm of a `DO` line's loop-control test.
- **not taken** (red) — no measured run took the edge, and no argument says it cannot be taken. This is a statement about the search, not about the code: no case has yet been constructed that reaches the edge. Each such edge carries a *reach* note — the input the code reading says would reach it.

An **annotated unreachable** edge has a recorded claim (`xtask/fixtures-config/coverage.toml`, with a class and the reason) that no input reaches it. The claim is a code-reading argument about the reference's own source, never "we could not build a case" and never a statement about yFoil. Every claim is falsifiable by the measurement: a case that takes an annotated edge makes the tool report the annotation as stale (this happened to `xoper.f:2784` branch 5, whose claim missed that MRCL's Mach clamp sets `M_CLS = 0`; the claim was withdrawn and the edge is now taken). The classes are:

- *structural* — impossible by construction of the data the analysis path feeds the routine: coincident consecutive nodes that `LOAD` removes, `IBL ≤ 2` inside an `IF(IBL.GT.3)` block, a quantity kept positive by every update that touches it, a subroutine only ever called under the flag it tests;
- *mode* — guarded by a flag the analysis path never sets: inverse design (`GEOLIN`), the image airfoil (`LIMAGE`, whose only toggle is commented out), flap hinge moments, interactive prompts. These are features outside yFoil's scope, and the edges are unreachable in XFOIL too when driven as the fixture pipeline drives it;
- *guard* — array-bound and illegal-input `STOP`s on Fortran's fixed dimensions (`IVX`, `IWX`, …); yFoil has no fixed dimensions and the cases are within XFOIL's;
- *compiler* — edges gfortran emits that correspond to no decision in the source;
- *numerical* — reachable in principle, but only by a floating-point coincidence (a real landing bitwise on a comparison's other operand: the stagnation point exactly on a node, SETEXP's initial guess exactly 1.0) or by exhausting the iteration cap of a Newton iteration that converges on every analysis-path input (SETEXP's 100, SINVRT's 10, MRCHUE's 25 at the similarity station). No input can be designed to reach them; if anything does, it is the parameter/fuzz harness.

A **DO-line edge** comes from the control test a Fortran `DO` loop is compiled with: *iterate again* or *leave the loop by its count* (the count exhausted, or zero to begin with). gfortran attributes that test to the `DO` line as a pair of edges, and the measured counts show two shapes: for a top-tested loop the second arm is the loop's normal completion, taken once per execution; for a loop gfortran rotated, the real exit sits on the loop's last statement and the `DO` line's second arm is a duplicate that is never taken. Neither arm is a body that ran zero times as distinct from a body that ran and finished: the analysis path's station, node and wake counts never make a loop empty, and the counts cannot tell an empty pass from a completed one. The *iterate* arm is an ordinary edge, taken whenever a run executed the body, and it appears in the branch map beside its partner. The grey DO-line edges are the never-taken second arms: a loop always left early by a `GO TO` or `RETURN` (its normal completion never happens), a rotated loop's duplicate, or both arms of a loop inside a block that is never reached. Whether each loop's body actually ran on the set is stated explicitly, from the execution count of the first line of its body, in the table *DO loops of the analysis path* below. A `DO` line that is an iteration budget (a Newton loop that could be exhausted: SPECCL's twenty attempts, SPECAL's CL(M) loop) is different: its second arm is the exhausted budget, a real outcome, so it carries a reach note and both arms are counted like any other conditional.

The same classes, with every annotated edge and its reason, are listed in [Coverage](../../development/testing/coverage.md); that page is the union over every tracked case, this one the minimal set.

## Which cases are candidates

Every tracked solver case is measured one at a time, and those with a finite reference run are the candidates for the finite set (counts in the table above). A case whose reference prints `NaN` is not a candidate: a non-finite trajectory cannot be compared as a whole run (NaN comparisons and `MIN`/`MAX` are where two correct codes legitimately differ), so the branches only such a run reaches are tested as events instead.
